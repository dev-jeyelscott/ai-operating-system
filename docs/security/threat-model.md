# AI Operating System Threat Model

- Version: 2.0
- Status: Final MVP security-review baseline
- Ticket: AIOS-150
- Review owner: Security Reviewer
- Approval owner: Product Owner
- Review cadence: Every material trust-boundary or privileged-capability change

## 1. Scope

This threat model covers the simulation-first MVP:

- Authentication, organizations, memberships, and project isolation
- Project configuration and encrypted integration credentials
- Document upload, processing, review, approval, and context snapshots
- Deterministic workflows, commands, events, retries, approvals, and audit
- Real Notion publication and reconciliation
- Simulated Layer 1, Layer 2, and Layer 3 provider execution
- Ticket selection and execution leases
- Notifications, operational read models, Reverb, and the 3D office
- PostgreSQL, Redis, Horizon, S3-compatible artifact storage, and CI
- Backup, recovery, deployment configuration, and supply-chain controls

The following capabilities remain outside the MVP:

- Real autonomous repository modification
- Real branch creation, commits, pushes, and pull requests
- Real CI evidence generated by an execution provider
- Real merge execution
- Production deployment initiated by an agent
- Unrestricted provider network or command execution

Out-of-scope capabilities must remain deterministically disabled. Their absence
is a security control, not evidence that they are safe to enable later.

## 2. Security objectives

1. Prevent access across organization and project boundaries.
2. Prevent provider or document content from changing authorization policy.
3. Prevent secrets from entering prompts, logs, artifacts, notifications, or UI payloads.
4. Prevent duplicated or unauthorized external side effects.
5. Preserve workflow, evidence, approval, and audit integrity.
6. Distinguish simulation, reported state, observed state, and verified state.
7. Reject unsafe production configuration.
8. Fail safely during external integration, queue, storage, and provider failure.
9. Preserve recoverability without bypassing authorization or evidence gates.
10. Prevent release while a Critical or High security finding remains unresolved.

## 3. Protected assets

- User identities and authenticated sessions
- Organization membership and role assignments
- Project data and configuration
- Approved source-of-truth documents
- Immutable project context snapshots
- Notion credentials and synchronized task content
- Provider and runtime credentials
- Workflow definitions, instances, transitions, and approvals
- Ticket selection state and execution leases
- Provider requests and provider results
- Artifacts, evidence, findings, and merge recommendations
- Audit history and correlation information
- In-app notifications and real-time projections
- PostgreSQL data
- Redis operational state
- S3 production artifacts
- Backups and restoration material
- CI configuration, lockfiles, and release artifacts

## 4. Threat actors

- Unauthenticated internet user
- Authorized project member
- Malicious or compromised organization member
- Compromised administrator account
- Compromised browser session
- Malicious uploaded document
- Malicious Notion content
- Compromised Notion integration
- Malformed or malicious provider result
- Compromised dependency or CI action
- Compromised queue message
- Compromised future execution provider
- Accidental operator error
- Insider with infrastructure access

## 5. Trust boundaries

1. Browser to Laravel HTTP application
2. Browser to authenticated Reverb channel
3. Laravel application to PostgreSQL
4. Laravel application to Redis and Horizon
5. Laravel application to S3 or MinIO
6. Laravel application to Notion
7. Laravel workflow engine to execution-provider adapter
8. Queue producer to queue consumer
9. Application state to operational and office projections
10. CI runner to GitHub, registries, and dependency sources
11. Deployment process to production configuration
12. Backup process to backup storage and restoration environment
13. Future execution provider to isolated repository workspace

## 6. Governing security invariants

- Authorization is decided by Laravel policies and application services.
- Provider output cannot grant permissions or bypass transition guards.
- Documents, tickets, repository content, logs, and provider output are untrusted.
- Every project-scoped query and command must enforce tenant context server-side.
- Secrets are stored only through approved encrypted credential mechanisms.
- Secrets are redacted before logging, persistence, notification, or provider dispatch.
- External side effects must be authorized, idempotent, and reconcilable.
- Workflow transitions must be deterministic, schema-valid, and auditable.
- Redis must not be the sole authoritative store for durable business state.
- Simulated output cannot become Verified evidence.
- Automated pull-request targets must remain `develop`.
- Automated changes to `main` are forbidden.
- Critical and High findings block security sign-off.
- Real repository execution remains disabled for the MVP.

## 8. Abuse cases reviewed

### 8.1 Tenant identifier substitution

An authenticated member replaces an organization, project, document, ticket,
execution, notification, artifact, or event-stream identifier with one from
another organization.

Expected result:

- Request is rejected with a safe 403 or 404.
- No resource metadata is disclosed.
- No audit or notification payload contains foreign project content.

### 8.2 Malicious document instruction

A document instructs a provider to ignore policy, reveal credentials, approve a
roadmap, modify workflow state, or execute an external action.

Expected result:

- Content remains untrusted project data.
- Deterministic policy remains authoritative.
- Suspicious content is flagged.
- Sensitive data is redacted before provider dispatch.

### 8.3 Malformed provider success result

A provider reports success while omitting required fields, using an invalid
target branch, reporting Verified evidence from simulation, or requesting
unauthorized capabilities.

Expected result:

- Result is rejected.
- Workflow cannot advance.
- Rejection is safely logged and audited.
- Retry or human escalation follows deterministic policy.

### 8.4 Duplicate command or external write

A client, queue worker, or integration retries a successful request.

Expected result:

- Existing result is returned or reconciled.
- No duplicate workflow, Notion ticket, execution, artifact, or decision is created.

### 8.5 Secret-bearing failure

An integration exception contains a token, authorization header, URL
credentials, connection string, or request body.

Expected result:

- Persisted and displayed error content is redacted.
- Raw secret values do not enter logs, audit events, notifications, or browser payloads.

### 8.6 Unauthorized Reverb subscription

A user requests a project or organization channel outside their membership.

Expected result:

- Channel authorization fails.
- No project event or existence metadata is returned.

### 8.7 Unsafe production environment

Production is configured with debug mode, HTTP, insecure cookies, local storage,
Mailpit, MinIO, non-Redis queues, or insecure Reverb credentials.

Expected result:

- Production validation fails.
- Deployment or startup verification cannot be considered successful.

## 9. Residual risk policy

- Critical and High findings cannot be accepted for the MVP release.
- Critical and High findings must be Mitigated or proven False Positive.
- Medium findings may be Open or Accepted only with:
  - a named owner;
  - a concrete due date;
  - documented impact;
  - evidence and compensating controls.
- Low and Informational findings are tracked where useful.
- Enabling real repository execution requires a new threat-model review.
- A security sign-off does not authorize post-MVP privileged capabilities.

## 10. Sign-off evidence requirements

AIOS-150 requires:

- All dependencies AIOS-010 and AIOS-137 through AIOS-149 marked passed.
- Relevant automated test results.
- Composer validation, audit, lint, static analysis, and backend test results.
- Frontend format, lint, type-check, unit-test, and build results.
- PostgreSQL concurrency evidence.
- Playwright and accessibility evidence.
- Production configuration validation evidence.
- Backup and restore evidence.
- Deployment and rollback evidence.
- Manual tenant-isolation, redaction, upload, provider-result, event-stream,
  simulation-labeling, and security-header review.
- Named Security Reviewer approval.
- Named Product Owner approval.
- No unresolved Critical or High finding.

The machine-readable result is stored in:

`docs/security/security-review.json`

The consolidated review evidence is stored in:

`docs/evidence/aios-150-security-sign-off.md`

## 11. Mandatory review triggers

Review and reissue the sign-off when:

- Organization or project authorization boundaries change.
- Authentication or session behavior changes.
- A new upload type or parser is enabled.
- A new external integration is added.
- Provider capabilities or result contracts change.
- Real repository read or write capabilities are enabled.
- Deployment or merge capabilities are enabled.
- New sensitive-data categories are stored.
- Storage, queue, event-stream, or backup architecture changes.
- A Critical or High incident occurs.
- A material architecture decision replaces an approved baseline.

## 12. Final decision rule

The release security gate passes only when the deterministic validator confirms:

- decision is `approved`;
- required human reviewers are named;
- all hard dependencies have evidence;
- all evidence paths exist;
- every Critical and High finding is closed;
- accepted residual findings have an owner and due date.

A passing automated command is necessary but not sufficient by itself. Human
review and truthful evidence remain mandatory.
